O que trava a construção

As telas ausentes não são só trabalho de UI. Três coisas precisam existir antes — ou em paralelo.

O app não tem navegação de detalhe

Ainda trava. As 4 chamadas de rota do app continuam sendo router.replace: não existe um <Link>, um router.push nem uma rota de detalhe. O M-SPLASH abriu a primeira divisão real — / virou o splash e a home foi para /inicio, levando a árvore de 6 para 7 rotas — mas empilhar tela sobre tela ainda é impossível. Ficha de jogador, detalhe de decisão, dossiê do adversário: nenhum tem para onde navegar. Continua pré-requisito de quase todo o L-M03.

Autenticação existe no cliente, mas a API ainda não a exige

Destravou em parte. O Clerk (R-171) passou a ser o provedor: o cadastro cria conta real, com e-mail verificado por código — exercitado no simulador. Some a trava antiga de "não existe e-mail nem verificação de credencial". O que ainda trava: POST /auth/session continua emitindo Bearer para qualquer subject, sem prova, então autenticar no Clerk ainda não é autenticar no jogo. Enquanto a API não verificar o token, M-LOGIN não fecha e a tabela de usuários do admin lista só o DEV_SUBJECT. Apple segue indisponível: desabilitado na instância e exige conta Apple Developer + development build (não roda em Expo Go).

Sem app publicado, telas que apontam para a loja não fecham

O doc do M-SPLASH pede que o bloqueio de contrato BREAKING traga "link à store". O app não está publicado, então não existe URL para linkar — o bloqueio funciona e impede o uso, mas o jogador fica sem ação possível. Mesma trava atinge M-STORE, M-SEASON-PASS e a atualização forçada. Inventar um link seria fingir.

O registro das telas não vigia nada

O screen-registry.ts não é importado por nenhum arquivo do app — só pelo próprio teste e pelo registro de golden paths. O cabeçalho dele afirma satisfazer FR-010 e SC-003 e que a falta de wireframes "não é lacuna", mas o dado é inerte: nada liga os 114 IDs às 6 telas reais, e o teste só mede o comprimento de um array.

O lado da leitura é grosso demais

Os docs especificam 78 queries finas por tela (GetFinanceSnapshot, GetBudget, GetCreditCapacity, GetBoardMessage…). A API expõe 15 queries grossas, uma por contexto — club, ledger, market. Commands não são o gargalo: existem 148. Cada tela nova ou deriva no cliente, como o club-projection.ts já faz, ou ganha projeção própria no servidor.

Nada disso é verificável hoje

Não há harness E2E — nem Detox, nem Maestro, nem Playwright — e apps/mobile/package.json não tem script de teste. O vitest inclui só .test.ts, então nenhum componente é renderizado em teste algum.

Os 16 golden paths não cobrem o produto

Os fluxos de UX vão até MF-25. Fechar GP-001…016 ainda deixa de fora treino e condição, imprensa, convocação para seleção, automações, estádio e loja — que respondem por boa parte das telas L-M03, L-M04 e L-M09.
